# Security policy

## Supported versions

Open Trestle is pre-implementation. No release is currently supported for production use.

## Reporting a vulnerability

Do not report vulnerabilities in a public issue. Once the GitHub repository is created, use its private vulnerability-reporting channel from the repository Security tab.

A report should include the affected revision, impact, reproduction steps, and any relevant proof. Do not include credentials, customer source, tokens, or exploit payloads that would create unnecessary risk.

## Response goals

Maintainers aim to acknowledge a valid report within three business days, assess severity and scope, coordinate a remediation plan, and publish an advisory when a fix is available. These are response goals, not a warranty or service-level agreement.

## Security design commitments

The project intends to enforce least privilege, immutable evidence, strict tenant and repository scope, provider-route policy, default-deny execution networking, and explicit authorization for dynamic validation. These are planned product controls until a released version demonstrates them with test and release evidence.
