# Changelog

All notable changes to released versions of Open Trestle will be documented in this file.

## Unreleased

### Added

- Added `trestle --help`, `trestle -h` and `trestle help`. Each prints the usage to standard output and exits 0, with the commands grouped as Everyday, Setup and keys, Integrations, Operators and Evaluation. A bare `trestle` without a terminal and an unknown command still print the usage to standard error and exit 2. The usage now opens with a pointer to the guides.
- Added reference pages under `docs/`: an index grouped by task, every command and flag, exit codes per command, every `failure_detail` value, environment variables and file locations, platforms, install, troubleshooting and privacy. See [docs/README.md](docs/README.md).
- Added `trestle update` for the packaged Linux amd64 install. It finds a strictly newer build, shows it, asks for confirmation (or takes `--yes`), runs that build's own `verify-archive`, then runs `sudo -- <copy> upgrade` on the terminal and reports the new version and source revision. `--check` only reports, with exit `10` when an update is available, `0` when none is and `1` on an error. `--from FILE` installs a named archive. GitHub releases of `georgejieh/open-trestle` are read with one unauthenticated, bounded GET. A release qualifies only when the archive's Ed25519 signature verifies with a key pinned in `internal/update/release_keys.txt`. The signature covers a statement of the archive's version, target, tag, SHA-256 and size. No key is pinned yet, so the release channel refuses with "this build cannot verify releases; install the packaged release". A development install also reads `~/.local/share/open-trestle/updates/`, a private `0700` folder, and labels its build as an unsigned local build. Every check runs in Go, on a copy in a fresh private folder, before any code from the candidate runs, and the copy is rechecked just before it runs. After at most one release list GET a day, the home screen and `trestle review` (on a terminal) show "Update available: X (you have Y). Run trestle update." The answer is cached in the state folder, and `OPEN_TRESTLE_UPDATE_CHECK=off` turns the check off. On a packaged install the home screen also adds an "Update Open Trestle" action. Added `tools/signrelease`, an offline Go tool that signs a release archive, prints its public key line and verifies it. No release workflow or key is added. See [updates](docs/updates.md).
- Added commit messages as stated intent to `trestle review` and `trestle local-git model-review`. The direct review reads the commits of `base..head` from the same verified Git objects that source acquisition read. These are the commits reachable from head and not from base, painted newest commit time first as git's merge-base walk does, with at most 1,024 commit objects and 4 KiB of each message. The context-assembly handler (identity version 8, `WithChangeIntent`) carries them as the generation context's `stated_intent` object, oldest first, labelled `author_stated_unverified`. The object holds at most 16 commits, 2 KiB each and 16 KiB in all. Text is cut on a character boundary and marked `truncated` with the full size, commits past a bound are counted in `commits_omitted`, non-text messages are kept without text, and `range_incomplete` is set when the walk stopped at its bound or at a missing parent. The text counts toward the 128 KiB source budget, filling what the selected sources leave. Each message carries `risk_flags` from the current content rules and is secret-scanned before remote egress as a new `stated_intent_text` field role (sanitized egress receipt v1, in place). It never enters the system channel and never changes the run plan, policy, routing or source selection. The verifier receives the same object. The walkthrough adds a stated intent line. In JSON it is `walkthrough.stated_intent`, with at most 8 subjects, control and format characters replaced and each subject cut at 120 characters. Text quotes the subjects, and Markdown adds a `### Stated intent` section with code spans. A run whose context carried commits declares change intent in its change features, so the `drift_auditor` intent condition now fires under `--specialists auto`. The daemon reads no commit messages, pull-request text or linked issues yet. See [commit messages as stated intent](docs/local-model-review.md#commit-messages-as-stated-intent).
- Added deterministic pattern hygiene (`internal/patternhygiene`). Every generation context except an investigation context records a `pattern_hygiene` object, computed from the acquired snapshots with no model. It reports three kinds of problem. First, 13 curated anti-patterns for Go, JavaScript and TypeScript, and Python are counted in the base and head of each changed file's directory, and reported when the head count is higher (spreading when the base already had it). Second, lint and type suppressions, workaround-justifying comments and TODO markers without an issue reference are reported on added lines. Third, absolute `NEVER`, `ALWAYS` and `MUST NOT` rules added to agent instruction and skill files are reported. A suppression on or beside a workaround comment is a deterministic `root_cause_not_fixed` note of severity low. Matching is lexical, over a line lexer that keeps string literals and comments apart. At most 32 directories, 128 files a side and 8 MiB of base text are compared, and a directory past a bound is not compared at all. The object holds complete counts and at most 16 items placed on changed sources by `source_id` and line, with no repository text. The walkthrough reports it in `verified.pattern_hygiene` (each item `origin` `deterministic`). In text and Markdown it appears as a `pattern hygiene:` line with the anti-pattern increases and the root-cause notes. It never changes status, CI disposition or exit code. See [pattern hygiene](docs/local-model-review.md#pattern-hygiene).
- Added nuance traps to the `bug_hunter` and `frontend` skills, both now profile version 2. They cover Go goroutine and channel leaks, `defer` in a loop, loop-variable capture before Go 1.22, `time.Sleep` and library `panic`, Python mutable defaults and bare `except:`, and React `useEffect` and imperative timers, with a pointer to lines `pattern_hygiene` cites.

- Added deterministic ranking, deduplication and a pre-existing class to `trestle local-git model-review` and `trestle review`. All three are decided after independent verification, with no model call. One shared rule (`localreview.DeduplicateFindings`) merges verified findings within a run, across specialist set members and across repeated runs. Two findings merge when they share path and side, the range overlaps the representative's, the categories are the same or of one family (security is its own), and the normalized title and claim are near-identical (four fifths of the distinctive words shared, no differing identifier or number). A second, location-anchored pass merges paraphrases of one defect ("Avg may divide by zero" and "Avg panics on empty slice"). It requires the same path and side, overlapping ranges, categories of one family that is not security, and either the same changed declaration of the semantic-impact profile or, when no changed declaration holds them, one range of at most five lines. Security findings merge only by the strict rule, and so does an uncategorized finding. The strongest verified finding represents the group at its own location, and the other wordings are kept: text and Markdown show `also reported as:`, and set JSON has `merged[]` with each member, title, claim and `rule` (`near_identical`, `same_declaration` or `same_lines`). A direct result records `declaration_anchors`, the changed declaration that holds each anchored finding. The import checks them against the findings and uses them to re-derive `rank`. `localreview.RankFindings` orders by severity, then by the number of origins that confirmed the defect and their independence, then by distinct evidence and a narrower range. A finding is pre-existing when it lies only on unchanged head lines (outside changed lines and 8-line deletion windows, from a fresh bounded diff) and cites no changed-hunk or removed-lines evidence. Only direct runs classify. A completed direct run's result (schema version 6, in place) adds `rank` and `pre_existing`. A result whose every finding is pre-existing keeps status `findings` with `ci_disposition` `inconclusive` (exit 3 by default, 0 under `findings` and `always-zero`, 3 under `strict`), and a review set follows the same rule. `localreview.ParseCompletedResult` re-derives `rank`, treats an imported `pre_existing` list as advisory and requires the readiness disposition, refusing a relaxed one. See [ranked findings and the walkthrough](docs/local-model-review.md#ranked-findings-and-the-walkthrough).
- Added a verification-led walkthrough to direct review results (`walkthrough`, schema version 6, in place) and review sets. It shows what was verified: secret-scan receipt totals, which local-only requests also have, the deterministic static checks, style detection, the semantic-impact profile and the verifier's confirmed, rejected and inconclusive counts. It adds a per-file change summary (added, removed and changed Go declarations, line counts from a fresh bounded diff, exact-content renames). It also lists missing verification: changed functions and methods that no test file references, taken from the affected-test candidates, as an informational class that never changes status. The walkthrough is bounded, and it is omitted with `walkthrough_omitted_output_limit` rather than truncated.
- Added `--format markdown` to `trestle local-git model-review` and `trestle review`. It writes a pull request summary comment with what was verified, the changes, missing verification, the confirmed findings in rank order (a set names the members that confirmed each) and the pre-existing findings. Untrusted text is escaped and cannot open links, HTML, headings or mentions or become an autolink. Added `--all`, which lists every confirmed finding in text and Markdown. By default they list high, critical and medium findings and count the rest. When no confirmed finding is high, critical or medium, they list the lower-severity ones instead, at most ten in rank order, and count the rest, so the output never hides every finding (this also applies to the first review in `trestle init`). SARIF lists results in rank order with `trestleRank` and `trestlePreExisting`.

- Added `trestle review` without a fixture path. In a repository that `trestle init` set up, it reviews the latest change, `HEAD` against its merge base with the default branch, in one step. It finds the setup folder the way `trestle init` does (or `--directory PATH`), keeps the saved review command's route inventory, runtime policy, tenant, repository and source labels, egress and timeout, and replaces only the two commits, which it picks on every run. The base is one `git merge-base HEAD BRANCH origin/BRANCH`, so a local default branch that is behind or ahead of `origin` does not pull commits already on the other into the review. On the default branch itself only `origin`'s copy counts, so unpushed commits are the change. `--base REF` and `--head REF` pick commits exactly, and `--format`, `--timeout`, `--profile`, `--specialists`, `--max-specialists` and `--exit-code-policy` pass through to the unchanged `trestle local-git model-review` path, whose result, egress, secret-scanning and spending messages and exit codes it keeps. It says when uncommitted or untracked changes are not included and that committing them includes them, and it never writes into the repository. It stops with exit 3 before sending anything when there is no setup, no committed change or no API key. `trestle review <path>` still reviews a fixture file. See [getting started](docs/getting-started.md#running-it-again).
- Added hidden API key entry to `trestle init`. When the chosen remote provider's key variable has no key in the environment or the credential store and standard input is an interactive terminal, the wizard asks for the key with the terminal's echo off (stdlib termios on Linux and macOS, the console mode on Windows; no new module). It restores echo before printing anything else, also on Ctrl-C or end of input, and never reads a key when echo cannot be turned off. It checks an OpenRouter key with one free `GET /api/v1/key` and asks again when OpenRouter refuses it (HTTP 401 or 403). Ollama Cloud and OpenCode Go keys are kept unchecked with a note. "Save this key for future reviews?" saves the key only once the setup is saved, so a declined setup writes nothing. `n` keeps the key in memory for the session and prints `read -rs NAME && export NAME`. Without a terminal or with `--no-input`, nothing is asked. A re-run of `trestle init` asks the same way when the setup's key is missing. `spending.OpenRouterKeyStatusError` now carries the status of a refused key read. See [API keys](docs/keys.md).

The folder is `0700`, and each variable name has one `0600` file holding exactly the key. - Added per-key spending limits and a local usage ledger for `trestle local-git model-review`, a new `trestle usage` command and an optional spending question in `trestle init` (see Changed). A limit belongs to one API key, keyed by the provider ID and the credential reference identity that setup already records for the key variable (`runtimeconfig.CredentialReferenceIdentity`, the same derivation for every remote provider), so every setup that names the variable shares it. A limit has an amount in whole cents, a calendar period in UTC (`week` from Monday, `month`, `year`) and alert percentages (default 80 and 100). Before each review run, and before any credential is read for model dispatch or any request is sent, a key whose recorded spend in the current period is at or over its limit refuses the run. The refusal uses the new closed failure detail `spending_limit_reached` (failure `policy`, status `refused`, CI `blocked`, exit 4, `run_status` `not_opened`, result schema version 6 without `token_usage`) and a hint naming `trestle usage`. A run whose worst case (two requests at the per-request bound, or an investigation policy's budget) could pass a limit runs with a warning. After a run that sent at least one request, one entry is appended under a file lock. It records the time, review run ID, runtime policy identity, keys, models, requests sent, `usage_known` and the cost. The cost is the settled `actual_cost_micro_usd` (`cost: settled_usage`) or, when usage is unknown, every sent request at its settled cost or its reservation (`cost: reservation_upper_bound`), always with `price_basis: route_max_price`. A crossed alert percentage prints one line such as "Spending alert: $8.12 of your $10.00 monthly limit for OPEN_TRESTLE_PROVIDER_OPENROUTER (81%)". Review set members are checked and recorded one by one, so a member refused at the limit stops the set. Spending lines go to standard error, and text output ends with each limited key's state. Every message says that the figures are an upper-bound estimate at the highest pinned price, not a bill, and that the limit is best effort with the provider's own limit as the guarantee. Routes on this machine and the Ollama sign-in route use no key and are not recorded, and a usage folder that cannot be read is reported and never blocks a review. `trestle usage` shows every limited key and every key with spend this month. For an OpenRouter key whose variable is set, it adds OpenRouter's figures from one bounded `GET https://openrouter.ai/api/v1/key`. Only the numeric usage and limit fields and `limit_reset` are read, never the key's `label`, and a failed read says "OpenRouter's usage could not be read". `trestle usage set --credential-env VAR --limit USD [--period week|month|year] [--alert 80,100] [--provider ID]` and `trestle usage clear --credential-env VAR` change limits. Records live in `$XDG_STATE_HOME/open-trestle/usage` (default `~/.local/state/open-trestle/usage`, mode `0700`, files `0600`) as canonical strict JSON under two new schemas, `open-trestle/spending-limit` v1 and `open-trestle/usage-ledger-entry` v1, with one ledger file per UTC month. They never hold a key, source, prompt or reply. `failure_detail` and result version 6 are not in any release and take the new value in place. The daemon does not record or enforce spending yet. See [spending limits](docs/spending-limits.md).

- `trestle local-git model-review` now recommends a standard style for each changed language that has a style detector but no style declared by the review's base tree. The style is read from the root of the base, never the head, as for `--specialists auto`, and EditorConfig alone does not count. A model review is nine tasks over eight stage kinds, not nine stages (README, `docs/local-first-bootstrap.md`). gRPC, OpenTelemetry, Docker Compose, Helm or Kubernetes manifests, Git-hook integration, policy-approved analyzers, compiler or language-server facts and historical co-change are marked as planned design (`docs/architecture.md`). `docs/getting-started.md` says early that remote providers need the packaged Linux amd64 install, and that a re-run reviews the commits pinned at setup, not the latest change. `docs/roadmap.md` now opens with the vision, lists what is available now and then the planned work, and no longer lists repository onboarding, which `trestle init` provides.

### Fixed

- `trestle review`, the `trestle` home screen and a `trestle init` re-run found a setup only in the folder `trestle init` proposes. A repository set up with `--directory` under `~/.local/state/open-trestle` was therefore reported as having no setup and was offered setup again. They now also find the most recently saved setup for the same checkout in another folder there. A setup counts only when it loads as a protected setup whose saved review command names this checkout, and at most 256 folders are read. A setup saved outside that folder still needs `--directory`.
- The `knowledge_graph` profile purpose no longer says it builds and extends the repository symbol and dependency graph. The profile is plan only, so no review run dispatches it and it builds no graph yet. The `style_conformance` purpose now names the styles its skill has guidance for (gofmt and Effective Go, PEP 8 with Black and Google Python style, Google C++ with clang-format, Prettier, ESLint and EditorConfig) and says that other declared styles, such as rustfmt and RuboCop, get none. - The container image declared port 8080, which nothing listens on. It now declares 8741, the daemon's default port. The Dockerfile and [operations](docs/operations.md) now say three things: `trestled` binds `127.0.0.1:8741` unless `--listen` names another address, a non-loopback address requires `--tls-cert` and `--tls-key`, and local review mode requires loopback.
- OpenRouter ZDR requests now allow fallback among the pinned endpoints. Profile `openrouter_zdr_chat_v2` sent `allow_fallbacks: false`, so OpenRouter served each request only from its top-ranked endpoint. When that endpoint failed, the review failed (a failing top-ranked endpoint failed the review as `transient` within about a second). V2 now sends `allow_fallbacks: true` with `only`. Fallback stays inside `only`: a request whose `only` listed no endpoint serving the model was refused with HTTP 404 although fallback was allowed. ZDR, `require_parameters` and the pinned set are unchanged, and the cost limit already uses the highest pinned price. The V2 adapter identity preimage is version 5. Profile V1 keeps `allow_fallbacks: false`.
- OpenRouter ZDR requests no longer fix the endpoint order. Profile `openrouter_zdr_chat_v2` sent the pinned slugs as both `only` and `order`, cheapest first, so every request went to the first endpoint. Every finder request went to one gpt-oss-120b endpoint, whose serving faults (chat-template tokens around the answer, malformed JSON) failed runs. V2 now sends `only` without `order`, and OpenRouter balances across the pinned ZDR endpoints. ZDR, `allow_fallbacks: false` and `require_parameters: true` are unchanged, and the cost limit already uses the highest pinned price. The V2 adapter identity preimage is version 4 with `pinned_order: false`, and profile V1 keeps its single slug in `only` and `order`. No recorded format on main changes.
- An OpenRouter answer wrapped in exactly one outer Markdown JSON fence is now unwrapped before the same strict validation, as the Ollama sign-in profile already did. Before, it failed the review as an invalid document, although an endpoint that lists structured output support may still fence its JSON. Any other wrapping (a language other than `json`, nested fences, text around the fence, an unclosed fence) is still refused. No recorded format changes.
- The `trestle init` cost question said it limited what "one review" may cost, but the limit applies to each model request and a review sends two (one to each model), so a review could cost twice the stated limit. The question now asks for the most one model request may cost, the explanation says a review costs at most twice the limit, and the summary panel shows both (`at most $0.49 a request ($0.98 a review)`). The limit's meaning is unchanged. The OpenRouter limits line no longer says the output and context come from "the smaller of the two models" when zero data retention is required. They are the smallest any pinned endpoint of either model allows. A filtered model list now lists an exact ID first, then the same name under another vendor, then names that start with the text. Its "more" line counts only matches beyond the list. It used to count every unlisted model, so two matches read as "... 464 more". Dollar amounts show whole cents (`$0.10`, `$3.30`), and wrapped lines in the first review's result box are indented under their value.
- An OpenRouter setup no longer lets one endpoint with a small output limit set the output of both models, and a review is no longer held to 4096 output tokens. Setup took the smallest context and output over every usable zero-data-retention endpoint of both models. For `openai/gpt-oss-120b`, one of 25 allowed 4096 output tokens and one 8192, while 23 allowed at least 32768. Every review also allowed 4096 output tokens (runtime policy `max_output_tokens`), so verifications by a model that reasons at length failed `model_output_exhausted`. `trestle init` and `setup bootstrap init --provider openrouter-zdr` now aim for a 16384-token review output allowance (`--max-output-tokens` sets it and `--output-tokens` caps it). For each model they pin only the usable ZDR endpoints that allow at least that much. The route's declared context and output, the pinned `provider_slugs` (sent as `only` and `order`), the prices (the highest over the pinned endpoints only), the policy's `max_output_tokens` and the wizard's cost-limit proposal all derive from that one set. The wizard says how many endpoints it left out and why ("2 endpoints that allow less than 16384 output tokens are left out") and how much each request may write. It also passes the allowance to the bootstrap so the bootstrap pins the endpoints the wizard showed. When no usable endpoint of a model allows the target, that model keeps all its usable endpoints as before and the allowance becomes the smallest output they allow (never below 4096). Both models are then pinned with that floor, and the wizard says so in one line. An allowance set with `--max-output-tokens` is never lowered: if no endpoint of a model allows it, setup stops and names the most that model's endpoints allow. With `--*-provider-slug`, the facts are those of the named endpoints. A slug that the API does not list as a usable ZDR endpoint of the model now needs the capacity and price flags, instead of borrowing the detected endpoints' facts. Without zero data retention (`--provider openrouter`) nothing is pinned, as before, and the allowance is 16384 within the smaller output the two models list. The "Limits:" line keeps its wording. The OpenRouter privacy witness observation records each endpoint left out for its output limit, with its tag and reported `max_completion_tokens`, in a new required `output_limit_endpoints_excluded` member. Witness version 3 and runtime policy version 8 are not in any release and have no published schema, so they take the member in place. See [what setup reads](docs/openrouter-zdr-profile.md#what-setup-reads).
- A model request through the OpenAI-compatible adapter's built-in HTTP client is no longer cut off after two minutes whatever its output allowance. A verification by a model that reasons at length can take well over a minute at a 4096-token allowance, and the 16384-token OpenRouter allowance makes that longer. The built-in client now gives each request two minutes per 4096 tokens of its output allowance, at least two and at most five minutes (a caller's earlier deadline still wins). The remote bootstrap's review command allows two such requests plus two minutes (`--timeout 12m` for a 16384-token allowance, and 10 minutes, as before, up to 8192 tokens). The built-in client's identity moves to version 3 of `open-trestle/openai-default-http-client`, which binds the five-minute outer timeout and that rule. The configuration identity of every adapter that uses it, and the model handler identities derived from them, therefore change, and a model task planned under the earlier identities cannot be claimed by the new handlers. A configured client, including the local inference client, keeps its own timeout. The client identity versions and the remote bootstrap are not in any release. See [OpenAI provider](docs/openai-provider.md).
- Every OpenRouter review failed as `internal` because the reply decoder refused OpenRouter's real replies. Real replies carry members the decoder did not know: a top-level `provider`, `native_finish_reason` on the choice, `reasoning` and `reasoning_details` on the message, and `image_tokens` in the completion breakdown. Some upstream providers also report more reasoning tokens than billed completion tokens (99 against 95 in one reply). The answer part (identity, choice, message, usage) is still decoded strictly, and it now knows those members and the rest of OpenRouter's published reply schema. Reasoning text is bounded and dropped. A choice error, returned images or a reasoning server-tool call is refused, and deferred tool turns must be zero. The completion breakdown, which settlement never used, is type-checked and no longer compared with the completion count. OpenRouter's routing metadata around the answer is no longer decoded strictly, because OpenRouter adds members there that its schema does not list. The upstream `provider` name must be a short printable string, and a reply whose `openrouter_metadata.pipeline` lists a stage other than an account guardrail (a plugin, server tool, response healing or context compression) is refused. Fixtures are OpenRouter's replies to a synthetic probe and to a setup review, and only the reasoning text of the review reply is replaced. No recorded format changes. See [how a reply is read](docs/openrouter-zdr-profile.md#how-a-reply-is-read).
- `sudo open-trestle-linux-amd64.pyz upgrade` and `rollback-version` on a real system (no `--destdir`) no longer stop with `error: --destdir must be an absolute path other than /` before changing anything. Checking the installed generation fed the resolved root `/` back into the `--destdir` parser, which refuses `/`. Only sandboxed `--destdir` lifecycles were tested, so every production upgrade and version rollback failed. Each lifecycle command now resolves its root once and passes it to the internal checks. A test runs install, upgrade, rollback-version, upgrade and uninstall without `--destdir`, and fails if a resolved root re-enters the parser. Install, verify-installed, rollback and uninstall were not affected, and no receipt, journal or archive format changes.
- A second `upgrade` of the packaged Linux candidate no longer stops with `error: upgrade rollback slot must be consumed before another upgrade`. The candidate kept its one rollback slot until `rollback-version` emptied it, so moving from one development build to the next meant rolling back first. Upgrade now moves the generation it replaces into the slot and discards the older predecessor in the same crash-safe transaction. The older predecessor's archive, sidecar, receipt and journal copies are verified like every owned file before anything moves, so a tampered or unsafe slot still stops the upgrade unchanged. The plan names that generation and binds the four copies before they are quarantined. They are removed only after the commit decision, so `recover` restores or completes the upgrade at every interruption point. Exactly one immediate predecessor is still retained, and `rollback-version` still restores only that one and consumes the slot. A retained predecessor that was itself an upgrade names the discarded generation, so its own lifecycle could not verify it if restored byte for byte. `rollback-version` now gives such a predecessor a `rollback-version` receipt and journal in that predecessor's own control schema 2 or 3. Every earlier lifecycle that can upgrade accepts that receipt shape, although none wrote it. Installed and rolled-back predecessors still get their exact bytes back. Transaction records are now version 2, with a `discarded_previous` member. This candidate still recovers version 1 records, and a lifecycle that reads only version 1 records refuses a version 2 record without changing anything. Receipt, journal, manifest and smoke schemas are unchanged. The opt-in SIGKILL matrix now also covers an upgrade into an occupied slot and the rollback after it. See [operations](docs/operations.md).
- A provider that refused a model request with HTTP 402 (no usage credit or quota), 404 (model or endpoint not served) or 410 (model retired) no longer fails the review as a bare `internal` failure with no task detail or hint. Every OpenAI-compatible request profile now classifies those statuses as the new closed route failures `payment_required`, `model_unavailable` and `model_retired` (the OpenCode console's 402 was `budget_exhausted`). None is retried, a payment refusal is not eligible for fallback, and the task fails once as a `policy` refusal, so the run is `refused`/`blocked` with exit code 4. When the provider's refusal of the most recent request ended the run, `trestle local-git model-review` records `failure_detail` `provider_payment_required`, `provider_model_unavailable`, `provider_model_retired`, `provider_authentication_failed` (401), `provider_authorization_denied` (403) or `provider_rate_limited` (429). It names the failing task and detail on the text `failure:` line and prints a fixed one-line `hint:`, and review set members carry the same detail and hint. The `trestle init` Ollama sign-in check names 402, 404 and 410 with the same hints (a billing refusal offers to continue, and an unusable model stops before writing). `setup bootstrap check --allow-local-probe` adds `messages` with the same reason when a model server refuses the probe. Neither makes a new request. The provider's error body is still discarded unread and never reaches a result, record, log or terminal. No parsed record on main carries a failed route outcome, so no recorded version changes. `failure_detail`, the completed-attempt record and the local-first bootstrap result are not in any release and take the new values in place, and other results keep their bytes. See [local model review](docs/local-model-review.md#provider-refusals).
- A daemon review now records the provider refusal that failed a candidate generation or verification task as its content-free failure reason (`provider_payment_required`, `provider_model_unavailable`, `provider_model_retired`, `provider_authentication_failed`, `provider_authorization_denied`, or `provider_rate_limited` for a 429). The reason is recorded in task completion v3, the v7 `task_failed` event and receipt v3, each only with its one run failure (`policy`, or `transient` for the rate limit). A failure before the request was sent records none. `trestle runs status` prints the reason on stderr with the local review's hint. The TUI shows a `Reason` and `Hint` line, the web console shows a labeled reason and hint, and the ACP review-state message shows a `Task failure` line. The MCP status tool returns the receipt unchanged. The formats that are not in any release, and their schemas, take the new values in place, and records without them keep their bytes.
- A provider that answers a model request with HTTP 200 and a reply the adapter refuses no longer fails the review as a bare `internal` failure whose hint could not tell a refused reply from an internal bug. The same holds for a status that no other class names (for example 409). A refused reply is malformed or truncated JSON, an empty or oversized body, or a Chat Completions reply with an unrecognized field. The run failure stays `internal`, the class the task already failed with, since the closed run failure set has no class for it. When that refusal of the most recent request ended the run, `trestle local-git model-review` records `failure_detail` `provider_response_invalid`. It names the failing task and detail on the text `failure:` line and prints the fixed hint "the provider answered, but its reply did not match what Open Trestle accepts, for example malformed or truncated output, an unrecognized field or an unexpected HTTP status: run the review again; if it repeats, choose another model or route and report it". Review set members carry the same detail and hint. A daemon run records it as the generation or verification task's failure reason, only with failure `internal`, in task completion v3, the v7 `task_failed` event and receipt v3. `trestle runs status`, the TUI, the web console (labelled "Provider reply refused") and the ACP review-state message show it with the same words, and the MCP status tool returns the receipt unchanged. `setup bootstrap check --allow-local-probe` now names a probe reply refused this way in `messages`, which it used to leave empty, and `trestle init` says the model server answered the test request with a reply not in the expected format. Three cases record no such detail: a request the adapter could not build or send, a review document that fails its schema after the reply was accepted, and an exhausted output allowance (`model_output_exhausted`). The reply and its field names never reach a result, record, log or terminal. `failure_detail` and the task completion, event and receipt versions are not in any release, so they and their schemas take the new value in place, and records without it keep their bytes. See [local model review](docs/local-model-review.md#provider-refusals).
- A model reply that stopped normally but whose answer was not a valid review document no longer fails the review as a bare `internal` failure that read like an internal bug. Candidate-generation replies from OpenRouter (`openai/gpt-oss-120b`, `finish_reason: stop`) were accepted by the adapter and then refused by the strict document parse. One wrapped its JSON in raw chat-template tokens (`<|start|>assistant<|channel|>final <|constrain|>...<|return|>`), and the other had a raw control character inside a JSON string. Refusing both stays correct, and nothing is stripped, unwrapped or repaired. The candidate and verification parsers now mark every refusal the answer itself caused (not one JSON document, a refusal, a malformed or wrongly shaped document, or one the review rules refuse). The generation and verification handlers record the new content-free task failure reason `model_output_invalid` with the task's unchanged `internal` failure. A host input check, and a reply that stopped at the output limit or at a content filter, record none. `trestle local-git model-review` records `failure_detail: model_output_invalid`, names it on the `failure:` line and prints the fixed hint "the model's answer was not a valid review document (for example malformed JSON, the wrong shape or a refusal): run the review again; if it repeats, choose another model". Review set members carry the same detail and hint. A daemon run records the reason, only with failure `internal`, in task completion v3, the v7 `task_failed` event and receipt v3. `trestle runs status`, the TUI, the web console (labelled "Model answer not a review document") and the ACP review-state message show it with the same words, and the MCP status tool returns the receipt unchanged. The answer's text never reaches a result, record, log or terminal. The task completion, event and receipt versions and `failure_detail` are not in any release, so they and their schemas take the new value in place, and records without it keep their bytes. See [local model review](docs/local-model-review.md#provider-refusals).
- A provider that rejects the request itself as invalid no longer reads as a refused reply. HTTP 400 and 422 (for example an unknown model ID, which OpenRouter answers with 400, or a parameter the model or endpoint does not accept) and 405 and 415 (a method or media type the endpoint does not take) were the route failure `invalid_response`. The review therefore failed `internal` with exit code 1 and, with the `provider_response_invalid` detail above, was labelled a refused reply ("Provider reply refused") with advice to run it again. Every OpenAI-compatible request profile, the OpenCode console included, now classifies them as the new closed route failure class `request_rejected` with no replay side effect. It is not transient and never retried, and it is not a provider outage (the setup probe reports it refused, not unavailable). Another route stays eligible for fallback, because it builds its own request for its own model, endpoint and parameters. The model handlers refuse the task as `policy`, like the other refusals of the request, so the run is `refused` with CI disposition `blocked` and exit code 4 after one attempt. `trestle local-git model-review` records `failure_detail` `provider_request_rejected`, names it on the `failure:` line and prints the fixed hint "the provider rejected the request as invalid, for example an unknown model ID or a parameter the model or endpoint does not accept: check the model ID, the endpoint and its transport, and that the model and endpoint accept structured output and the requested output allowance; then re-run setup". Review set members carry the same detail and hint. A daemon run records the reason `provider_request_rejected`, only with failure `policy`, in task completion v3, the v7 `task_failed` event and receipt v3. `trestle runs status`, the TUI, the web console (labelled "Provider request rejected") and the ACP review-state message show it with the same words, and the MCP status tool returns the receipt unchanged. `setup bootstrap check --allow-local-probe` names a probe rejected this way in `messages`, and `trestle init` says the model server refused the test request with the same detail and hint. A status that no class names, for example 409, stays `invalid_response`. The provider's body is still discarded unread. No published record can carry the new class: the route execution record v1 and the investigation turn v1 hold successful attempts only. The completed-attempt record, `failure_detail` and the task completion, event and receipt versions are not in any release, so they and their schemas take the new values in place, and records without them keep their bytes. See [local model review](docs/local-model-review.md#provider-refusals).
- A model request that the provider rate-limits is now retried on the same route at most twice, inside the candidate generation or verification task's one attempt, instead of failing the review at once. A rate limit is HTTP 429, or a 503 that names a `Retry-After` in seconds, and both are refusals before processing. A 503 without such a `Retry-After` stays a `provider_server` failure and is not retried. Each retry waits the provider's `Retry-After`, but at least the task's fixed retry delay, which also applies to a 429 without `Retry-After`. A `Retry-After` beyond 15 minutes or past the run's deadline is not waited for. Each retry is its own claimed, completed and settled route attempt whose authorization takes over the refused attempt's reservation, so the reservation is never made again or exceeded. A rate-limited attempt consumed nothing, so it records known zero usage and settles at zero cost. A review that needed a retry keeps that stage's usage and the run's cost known when the final attempt reports usage, and no other failure is assumed to cost nothing. After the second retry the task fails as `transient` with `provider_rate_limited`. The task-level `Retry-After` scheduling could never fire, because model tasks have one attempt, and it is removed along with its `retry_after_milliseconds` record field. The daemon's startup proofs of a failed run's model audit (a generation rejected for document shape, or an exhausted model lease, before or after retention lapses) accept that retry shape, so such a run boots cleanly. While its artifacts are retained, each retry claim must carry the identity the gateway grants for its lineage, and any other shape stays quarantined. No recorded format changes.
- A model reply that stopped at the output limit with no answer (`output_exhausted`) no longer discards the usage the provider reported. The OpenAI-compatible adapter keeps it under the same checks and profile rules as a successful reply's usage (the OpenCode console profile withholds native usage from both). The failed attempt's cost therefore settles from that usage exactly as a successful attempt's does, its tokens count in `token_usage`, and route continuation sees the settled balance. A reply without usage, or with usage those checks refuse, keeps unknown usage and the reservation stays held. So do HTTP errors other than a rate limit, transport failures and invalid replies. The failure classification is unchanged. The dispatch, outcome, reconciliation and completed-attempt records already carried usage for a failed attempt, so no recorded format changes and earlier records read back with their original settlement.
- A model reply that stopped at the output limit part way through its answer no longer fails the review as a bare `internal` failure with no detail. The OpenAI-compatible adapter classified a length stop (`finish_reason: length`, or a Responses `incomplete` result for `max_output_tokens`) as `output_exhausted` only when it carried no answer text. Answer text the model had not finished was returned and then refused by the strict document parser. On every request profile (generic Chat Completions and Responses, both OpenRouter ZDR profiles and a generic OpenRouter connection, OpenCode Go, the OpenCode console and the Ollama sign-in profile), a length stop whose answer text is not one complete JSON value is now `output_exhausted`. It keeps the usage it reported under the same rules as a reply with no answer, so `trestle local-git model-review` records `failure_detail: model_output_exhausted`. Its hint now reads "the model used its whole output allowance, usually on reasoning, before finishing its answer; choose a non-reasoning model for this role or raise the review output allowance (setup bootstrap init --max-output-tokens)". A length stop whose answer is a refusal or one complete JSON value is returned unchanged. No recorded format changes.
- The published artifact schemas now match every durable encoding. Each version has its own schema file. Candidate-batch v2 and v3, verified-finding-set v2 and v3, verification-batch v2, and model-generation-input v2, v3, v4 and v5 are new files (v2 and v5 are the investigation forms, which had no schema, and v5 records `removed_lines` evidence). The generation and verification result schemas accept each embedded version with `oneOf`, and the version 1 files of the candidate batch and verified finding set are again exactly as first published. Base-side locations, evidence sides and head lines, which those version 1 files never admitted, are described in the new files. Tests validate each encoding against its version's schema and check that no other model-generation-input version's schema accepts it. No published result schema embeds an investigation input.
- Published every receipt version the daemon embeds in an API response. `schemas/controlplane/api-response-v1.schema.json` allowed only review-run receipt v1 as `run`, while the daemon embeds receipt v2 (a linked context abstention) or v3 (a recorded failure reason), both introduced in this release. A client validating against the schema therefore rejected GET-run, submit and cancel responses for such runs. `run` is now receipt v1, v2, or v3. The envelope is unchanged: like `diagnostics`, which already lists diagnostic sets v6 to v8 added in this release, `run` names its record's own version. `schemas/controlplane/task-completion-request-v1.schema.json` had the same gap for the task completion v2 and v3 a worker sends, and now accepts completion v1, v2, or v3. The MCP `open_trestle.run_status` and `open_trestle.submit_run` output schemas fixed the receipt `schema_version` at 1, so their structured content for a receipt v2 or v3 broke the declared schema. They now accept 1, 2, and 3.
- A run whose final result had not been recorded when its 24-hour evidence retention lapsed (for example after a daemon stop between finalization and projection) no longer stops the model worker supervisor with an expired-artifact error. The daemon now records the result the run journal proves, marked `evidence_expired` and without evidence parts: canceled, failed or inconclusive, never completed. The web console shows the mark.
- A daemon that ran any local model review no longer refuses to start once that run's 24-hour artifact retention lapses (`historical prepared context input intent quarantined at startup`, with `runtime artifact expired` or `generation rejection physical proof refused`). A run the journal already settled (completed, canceled, failed by a rejected generation or an exhausted model lease, or an expired input that was terminated) is now proved from the journal and audit alone, without reading its expired artifacts or appending. Its receipt and result stay readable, and later runs continue. A run that is still active needs live retention as before.
- An added binary file under the 1 MiB diff bound is no longer labelled an empty added file. It is an `unsupported_content` gap (`analysis_unsupported_content` omission), and `empty_added_file` now means an added file with zero bytes. From deterministic evidence version 4, which exists only in this development candidate, readback refuses `empty_added_file` for any other added file. Versions 1 to 3 read back unchanged.
- A local model review whose route cannot take the sanitized context request no longer stops the daemon's model worker supervisor with `execute repository run: ... no eligible route`. The context task's owner now records the refusal within its packet lease as `route_context_insufficient` with the required, input, output and declared token counts, or `no_eligible_route`, on the run receipt. The run fails, the packet is retained, and later runs continue. A restart recovers the refused run without an append, including after the packet's 24-hour retention lapses. A refused or lease-expiry-terminated packet is then proved terminal from the journal and audit, without reading its expired bytes, and a refused run finalized after that still gets its failed result. Previously the daemon refused to start once such a packet's retention lapsed. If the lease expires between finding the refusal and recording it, the owner records the lease-expiry termination instead, and the supervisor keeps serving later runs.
- Removing a file over the 1 MiB change-model diff bound no longer fails the deterministic analysis task, and with it the whole review, with an internal error. A size limit is now recorded as a whole-entry `resource_limit` gap whatever the entry kind. A removed or emptied file over the bound also records its removed text as one whole-entry `removed_lines_limit` gap without reading it, and an added file over the bound that gets no reviewable range is no longer labelled `empty_added_file`. The rest of the change is reviewed, the review is not full clearance, and recorded results of deterministic evidence versions 1 to 3 read back unchanged.
- Made the investigation constructor pre-plan the exact first turn. It used to plan the first turn before reading the initial sources, so its context recorded zero scanned bytes while the first dispatched turn recorded their size. A route too small for that turn by a few bytes then passed construction and was refused at the first dispatch. The pre-plan now uses the scan total the initial reads must charge, and construction refuses unless the first turn request equals the planned one.
- Explained a review refused because its reservation exceeds the route's declared context. It used to read `failure: policy (task context)` with a hint about omitted sources. When no route is eligible and one was refused because the byte-based reservation (input upper bound plus output allowance) exceeds its `max_context_tokens`, the generation and verification authorizers and investigation turn planning now report a `gateway.RouteContextShortfall`. `local-git model-review` then adds `failure_detail: route_context_insufficient` and a `context_shortfall` JSON object (required, input, output and declared tokens), also on review set members, with a hint naming the tokens needed and what to raise.

It used to propose a listed model length, which is not proof of the server's setting, and it proposed nothing when the list stated none.
- `trestle init` now shows the complete packaged-build sequence from `docs/operations.md` when a development build cannot send source to a remote provider, including `python3 tools/vulnerability_gate.py --staging .container` and `verify-archive`. - Webhook intake now keeps running past a delivery that can never be planned. Reconciliation stopped at the first failing delivery and retried the whole pass. One stored delivery whose planning always failed (for example a payload the GitHub planner rejects) therefore exhausted the retries, stopped the supervisor, and blocked every later delivery. Planning errors, plans outside a delivery's lineage, and run-plan conflicts are now deterministic refusals. The supervisor records one content-free refusal per delivery, naming its planner identity, in the inbox (memory, file, and a new PostgreSQL `open_trestle_webhook_refusals` table, migration 0017) and skips it. A recorded refusal is terminal: the delivery is never processed again for that planner identity, so it starts no new retry cycle and never has its run opened later, and a later refusal with another reason keeps the first record. A delivery's own repeated failure is confirmed by probing that the run journal and artifact store still answer. It then backs off on its own schedule while other deliveries keep flowing, and is recorded as refused with `retries_exhausted` once its bounded attempts are spent. The retry state persists in the inbox, so a restart neither resets the bound nor retries early. It holds the count and next-attempt time, one state per delivery naming the planner identity that recorded it, and it includes a PostgreSQL `open_trestle_webhook_retries` table from migration 0018. State that a superseded planner left is replaced or pruned once the delivery is admitted or refused, instead of accumulating. In the file inbox, retry files are bounded apart from deliveries, one per delivery, and refusal records are bounded the same way, one per delivery. A superseded planner identity's record is kept until the current planner admits the delivery (then pruned) or refuses it (then replaced), so neither kind reduces delivery capacity or grows with planner changes. A delivery whose retry state finds no room is refused with `retry_capacity_exhausted`, so no delivery is retried forever. Only global failures (the inbox store or the probe) stop the supervisor. - Daemon GitHub pull requests are now reviewed from their merge base. The webhook planner reviewed `pull_request.base.sha..head.sha`, so once the base branch moved after the branch point, every newer base-branch commit appeared as a reverse change the pull request never made. The `source-base` task now takes source input v3 (the requested base and the head). It reads GitHub's merge base with one `GET /repos/{owner}/{repo}/compare/{base}...{head}?per_page=1` under the existing `contents: read` permission (only `merge_base_commit` is used, within the 16 MiB metadata bound, and the brokered transport accepts exactly that request shape). The change handler builds the change from the recorded merge base after checking it against the head the run acquired. A head equal to or already contained in the base fails with `nothing_to_review` (equal commits are now planned so the refusal is recorded). A merge base that GitHub does not report fails with `merge_base_unavailable`, and this includes every compare not found (so unrelated histories, since GitHub's message for them is not sourced). There is no fallback to `base.sha`. A force-pushed head is reviewed from its own merge base. The prepared GitHub planner identity moved to version 2. A run already opened by version 1 is resumed as that delivery's run under its recorded plan when that plan is exactly the one version 1 produces for the delivery with this daemon's task handlers, while new deliveries are planned from the merge base. - Every model list the fetch accepts now fits into the 8 MiB protected-file limit on `trestle config models refresh` and `apply`. Proposals and catalogs were written indented with HTML escaping, and each model stored its selector a second time inside a re-encoded copy of its object. A list near the 4 MiB fetch limit (long selectors, `<`, `>`, `&` or U+2028 in values, deep metadata) therefore produced a file over the limit, and refresh failed. They are now compact JSON with a trailing newline and no HTML escaping. Metadata is the rest of the model object with its exact members, and the selector is stored once, so a stored model is at most 20 bytes longer than its listed object. The file limit is unchanged, and catalogs and proposals written earlier still read back, apply and diff without spurious changes.
- The local structured-output `response_format` is now reserved in route planning. The generation and verification route authorizers, the local generation route plan and every investigation turn now reserve those bytes (`review.ModelRequestBudgetForTransport`) whenever a planned route's connection enables the option. Such an authorizer binds `input_transport` into its identity (verification authorizer identity version 3). Investigation planning reserved the request payload plus 256 bytes only, so a turn's approved estimate could fall below the host estimate (`review.ModelRequestBudget`) that the local structured-output check recomputes and enforces. Route capacity and cost checks also ignored the system message. Turns now reserve payload plus system channel plus 256 bytes under turn-record estimate version 2, which stores the counted bytes in a new `system_channel_bytes` member. - Deletion-only changes are now reviewed instead of refused. A change that only removes lines (for example a zero guard) failed the context task with `policy` / `all_sources_omitted` before any model call. The removed base lines now reach the generation, verification and investigation requests as `removed_lines` sources at their base line numbers, rebound to the exact base file and flagged like every other source. ### Security

- The GitHub Actions example (`examples/github-actions/open-trestle-review.yml`) put SARIF `message.text` and fix guidance, which are model output, and repository paths into the job summary unescaped. Reviewdog posted the same text as pull-request comments, so a finding could carry HTML, links, images, headings or @-mentions into GitHub Markdown. The workflow now writes a jq module that escapes untrusted text with the rules of `localreview.MarkdownText` and `MarkdownCode` (the `--format markdown` renderer), including autolink defusal. The job summary is rendered through the module, and reviewdog reads a copy of the SARIF whose message text is escaped and whose `message.markdown` is removed. The SARIF uploaded to code scanning keeps the raw text. The repository test runs the module with jq, offline, against crafted SARIF and checks it byte for byte against the Go renderer. The workflow itself is still unrun on GitHub.

- The daemon's GitHub publisher no longer lets model-written titles and claims become links. Its Markdown escaping now also defuses autolinks (a zero-width space before a scheme's colon such as `https:` or `mailto:`, inside `www.` and on both sides of `@`), as the new Markdown renderer does.

- A saved provider key is a plaintext file protected only by file permissions, like other command-line credential files. It is kept from other accounts on the machine, not from programs running as the same account, the administrator or backups. The environment always wins, so a key can stay in an external secret manager. On Windows the store's ownership checks are unavailable, so saving is refused and a typed key is used for the session only. A test sends a canary key through a full review in each output format and finds it only in the `Authorization` header: never in a request body, the output, the setup folder or the usage ledger. See [API keys](docs/keys.md#threat-model).
- Updated the Go build toolchain from 1.26.10 to 1.26.11 in the root module, the isolated secret-scanner worker, and the isolated govulncheck module, for GO-2026-6859. The worker binary vulnerability baseline was regenerated for the new build with no new identity, and three GO-2026-5841 `github.com/klauspost/compress` presence entries no longer appear and were removed.
