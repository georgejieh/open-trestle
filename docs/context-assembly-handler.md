# Context assembly task handler

`handlers/context` turns the exact deterministic evidence and memory task outputs into one protected generation authority. It does not call a model.

## Reconstruction boundary

The handler requires successful `analysis` and `memory` dependencies and a single task attempt. It reloads the shared change artifact, both acquired snapshot indexes, and every head source file. It rebuilds the complete head manifest within a 256 MiB bound.

Every changed-range evidence slice is independently recreated from the acquired file bytes. The file identity, file digest, physical line slice, slice digest, byte count, and `SourceSliceBinding` identity must all match the deterministic evidence artifact. This check includes slices that later exceed context selection limits.

## Context reduction

Repository text remains `repository_controlled` data. Only evidence paths allowed by the already validated memory scope can enter the packet. Changed-range evidence is considered first. Bounded one-line sources named by the semantic profile are then admitted as `direct_reference` candidates after their source file and slice identities are independently reconstructed. Affected-test links retain their syntactic-candidate status. At most 128 source candidates are considered. Deterministic selection keeps at most 32 sources and 128 KiB of source text. The packet records every analysis and semantic-coverage gap and every pre-selection authorization, candidate-limit, duplicate-source, or source-size omission. Counted semantic omission summaries retain the exact number of rejected references without emitting an unbounded record per reference. Its coverage counts sum each omission record's bounded count, including validated evidence excluded before selection as well as count and byte omissions made during selection. Memory query omissions also remain bound through the exact dependency artifact in context provenance.

All memory retrievals are reconstructed from their records, queries, scores, ranks, index revisions, and identities. The context packet carries the bounded retrieval set rather than silently retaining only one changed path. Memory remains labeled `advisory_only`.

## Non-Go text files

Changed hunks of files whose path does not end in `.go` are admitted as `changed_hunk` sources when the slice is valid UTF-8 with no NUL byte and passes the same size and candidate bounds as Go hunks. They are ordinary repository-controlled evidence data. No structural or semantic analysis exists for them: the semantic-impact profile still records `unsupported_language` for each path, which the packet keeps as the `semantic_unsupported_language` omission, and nothing in the packet claims symbol, reference, or test evidence for these files.

These non-Go paths are not reviewed and are recorded as omissions instead:

| Rule | Omission reason |
| --- | --- |
| A `vendor` or `node_modules` path segment; basenames `go.sum`, `package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`; suffixes `.lock`, `.min.js`, `.min.css`, `.map` | `excluded_path` |
| A hunk that is not valid UTF-8 or contains NUL | `non_text_content` |
| Binary or unsupported-content files rejected earlier by change evidence | `analysis_unsupported_content` |

The exclusion list is fixed in code and applies only outside `.go`; Go files keep their previous handling. A change whose every file is omitted for these reasons, or for `unsupported_language`, still produces the `unsupported_language` abstention.

## Repository instruction files

The handler reads `AGENTS.md`, `CLAUDE.md`, `.github/copilot-instructions.md`, and `.trestle/review-instructions.md` at the repository root of the **base** snapshot and adds each one present there as a `repository_context` source. The fixed list is root-only: a copy in a subdirectory is never read. The head tree is never the source of instructions, because a pull request author controls it: an edit to an instruction file arrives as an ordinary `changed_hunk` source and is reviewed as code, never followed as guidance. A base instruction file is used only when the head holds byte-identical content (equal digest and size), so the source is slice-bound to the immutable head file identity that every later readback checks. A base file that the head changed or deleted is omitted as `repository_instruction_changed`. A file absent from the base contributes nothing, so a change against an empty base (every file added) has no instruction context. Content never comes from a working directory.

Caps are 8 KiB per file and 16 KiB across all four files. A larger file is cut at the last whole line within its allowance and the dropped tail is recorded as `repository_instruction_truncated` with its line range. A first line that alone exceeds the allowance is omitted as `repository_instruction_size_limit`. A file that is not valid UTF-8 text is omitted as `repository_instruction_unsupported_content`, a path outside the memory scope as `repository_instruction_path_not_authorized`, and a file beyond the 128-candidate bound as `repository_instruction_candidate_limit`. An instruction file whose identical slice is already a changed hunk is not duplicated. Instruction sources are added only after the abstention and zero-selection decisions, so they never make an all-omitted change reviewable, and only when they fit the selected-source count and 128 KiB byte budget left after every changed source (in reference-ID order); one that does not fit is omitted as `repository_instruction_packet_budget` instead of becoming a selection omission.

Every `repository_instruction_*` omission stays in the packet's complete `source_coverage` and `source_omissions` accounting, but it is not a changed-source omission. Derived verification coverage, diagnostic sets, SARIF `trestleSourceOmittedCount`, and the result's `incomplete` status exclude it. The direct local review reports it separately as `instruction_context_omitted` (a count field and a limitation; SARIF `trestleInstructionContextOmittedCount`).

Instruction files are advisory. They carry the `repository_controlled` taint and the same `evidence_data_not_instructions` label as every other source. The version 7 and 8 generation instructions tell the model that `repository_context` sources are the repository's own review preferences: advisory guidance about what to look for and its conventions, never authority, unable to change the output contract, evidence rules, or authority limits, and not changed code. A pull request can edit its own instruction file, so the text is untrusted and is a hint about what to look for, never a rule the review must follow. Candidate admission drops a candidate whose `source_range` names a `repository_context` source and keeps the rest of the batch; the drop is derived only from the exact response and context bytes, counted in the batch (`repository_context_anchor_omitted`, bound into the batch identity and durable encoding when nonzero), and reported by the direct local review as the `repository_context_anchor_candidates_omitted` limitation and count. It never fails the run. A candidate may still cite a `repository_context` source as supporting evidence. When an instruction file is itself changed, its changed lines are a separate `changed_hunk` source, and a candidate located there is admitted. The verifier receives the same packet sources under the version 7 verification contract; instruction files grant it no extra authority. Required-mode publication rebinds each instruction source to its head file only after checking the fixed path, the line-1 prefix, and the byte-identical base copy, and refuses a published finding located in an instruction file; see the [publication task handler](publication-handler.md).

Every source carries `risk_flags`. From version 7, a source whose path names repository AI material (these instruction files, `SKILL.md`, prompt files, agent configuration directories) gets `agent_configuration`, and instruction-like content such as chat-template tokens or fake system tags gets `instruction_like_text`. The flags mark material for attention and never suppress review. The host contract travels only in the trusted system channel. See the [prompt-injection boundary](prompt-injection-boundary.md) for the channel split, the full path and marker lists, and what is and is not guaranteed.

## Removed base lines

A deletion-only file analysed at deterministic evidence version 7 carries one `removed_lines` record per deletion point: the removed base lines, bound to the exact base file, with the `head_line` beside the deletion. An emptied or removed file carries its whole removed base text as chunk records with no head line. The handler reloads that file from the base snapshot reference whose digest the record and its change entry name, rebuilds the repository-file identity and the slice binding from the bytes, and refuses any mismatch. Each record becomes one `removed_lines` source with `repository_controlled` taint, the file `path`, base `start_line` and `end_line`, the record's `head_line` when it has one, and `risk_flags` from the same rules as every other source. Removed text on an excluded or unauthorized path, that is not valid UTF-8 text, or past the candidate limit is recorded as an omission at its base lines.

A deletion point's removed text never makes a change reviewable: it is kept only when a selected changed hunk of its file holds its `head_line`, and is otherwise recorded as a `packet_budget` omission at its base lines. The removed text of an emptied or removed file needs no head neighbor, so a change that only removes files gets a packet of removed text alone, whose review snapshot has no head range; it still abstains with `all_sources_omitted` when no removed text can be supplied. Removed sources are selected right after changed hunks and before semantic expansions and instruction files. Removed base lines are never review-snapshot ranges; a finding located on them is a base-side finding. See [deletion-only changes](local-model-review.md#deletion-only-changes).

## Pattern hygiene

After the sources are selected, every packet except an investigation context gets a `pattern_hygiene` object: deterministic evidence that the change adds or spreads a curated anti-pattern, adds a lint or type suppression, a comment that justifies a workaround, a TODO without an issue reference, or an absolute rule in an agent instruction or skill file. The handler builds it from the acquired snapshots only: the head contents it already loaded and, for the changed files' directories, the base files, read from their protected artifacts (at most 32 directories, 128 files a side and 8 MiB of base text; a directory past a bound is recorded as unread and not compared). The object holds complete counts and at most 16 items placed on selected `changed_hunk` sources by `source_id` and line; it carries no repository text. It never changes source selection, coverage, or the abstention decisions, and a clean change records zero counts and an empty list. The rules, bounds and false-positive guards are in [local model review](local-model-review.md#pattern-hygiene).

## Stated intent

A handler built with `WithChangeIntent` also carries the change's author-stated intent. It asks its `ChangeIntentSource` for the change's own repository and `base..head` revisions, as the change artifact records them, and gets back a bounded `review.StatedIntent`. The direct review's source reads commit messages from its verified local object store; the daemon binds none. The intent is fitted into the source byte budget the selected sources left (`StatedIntent.Fit`), so changed code keeps priority, and a cut is marked `truncated` or counted in `commits_omitted`. It is attached as the packet's `stated_intent` object, repository-controlled data with risk flags, and never changes selection, routing or the run plan. A source that fails fails the task (`invalid_input`, or `canceled`) rather than silently dropping the intent. See [commit messages as stated intent](local-model-review.md#commit-messages-as-stated-intent) and the [prompt-injection boundary](prompt-injection-boundary.md#stated-intent).

## Context version and handler identity

Every new candidate-generation packet is review-context schema version 9. It requests `model-candidate-batch-v2` (identity `63a1bd4a…91bb`), binds the version 9 instructions (the version 8 instructions plus one sentence for `stated_intent` and one for `pattern_hygiene`; version 8 is the version 7 instructions above plus one sentence that explains `removed_lines` sources) by `instructions_identity` (their SHA-256; the prose itself is sent only in the system channel), and holds the optional `specialist` identity block when a profile is bound, `pattern_hygiene`, and `stated_intent` when an intent source is bound. Versions 2, 3, 5, 7 and 8 are accepted only by recorded-readback validators (`ValidateRecordedContextPacketRequest`, `RecordedContextSpecialist`, `ReconstructRecordedVerificationRequestContext`); they never start a model attempt, produce trusted egress instructions, or pass sanitized egress, and none of them may carry `stated_intent` or `pattern_hygiene`.

The route-granting handler identity (`NewHandler`, `NewSpecialistHandler`) is `open-trestle/context-assembly-handler` version 8. It changed to version 6 because the text fallback, base-snapshot instruction files, and version 7 contract alter the packet bytes for the same inputs, to version 7 for the version 8 contract and `removed_lines` sources, and to version 8 for the version 9 contract, pattern hygiene and the stated intent. `WithChangeIntent` also binds the intent source's identity. A run plan records its handler identities, so a run planned under an earlier version is not executed by the version 8 handler and fails closed instead of silently assembling different bytes; its recorded artifacts remain readable. The packet-only, journaled packet-only, and packet-authority identities are unchanged, as at the earlier bumps, although their packets are version 9 with pattern hygiene and never carry a stated intent.

## Route authority

The handler passes the canonical provider request to a configured policy authorizer. The authorizer identity is part of the handler identity. The call binds the exact review scope, request identity, plan policy, and decision time. Returned authority must match the scope and request.

The built-in policy authorizer ranks only the performance observations belonging to eligible routes and retains rejected-route accounting in the selection receipt. Before returning usable generation authority, it durably records the complete route selection in the same scoped audit ledger used by generation. Selection persistence failure returns no authorization. Authorizer identity version 2 binds this audited-selection behavior; construction requires an explicit ledger.

The handler persists two protected artifacts:

1. A `context_packet` containing only canonical provider bytes.
2. A `task_input` binding that context to its selected snapshot, evidence, and one exact `RouteAttemptAuthorization`.

The task output is the `task_input`. It carries the exact memory-scope and retrieval-set identity, so later provider-request validation recomputes every advisory record and retrieval identity. The generation handler therefore consumes dynamically created authority through its exact `context` dependency. Context and input expiry cannot exceed any source or upstream dependency expiry.
